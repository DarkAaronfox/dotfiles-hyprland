## Wi-Fi icon "not white" — actually fixed (2026-09-13, later same day)

The "hardware panel" verdict above turned out to be wrong, disproven by direct photographic evidence: the user photographed the media card's header row and showed the plain-`Text` clock (`Clock.qml`, color `#f5e2c5`, a warm *cream* — lower raw luminance than pure white) looking visibly **brighter** than the Wi-Fi icon supposedly colorized to `#ffffff`. If this were a display-hardware color cast, both elements — adjacent pixels on the same physical panel — would be shifted equally; a `Text` glyph looking brighter than an adjacent "white" icon is direct proof the icon itself isn't reaching true white, i.e. a real, local rendering bug, not a global display characteristic.

**Root cause**: `IslandHeaderRow.qml`'s `RowIcon` component recolored icons via `MultiEffect { colorization: 1.0; colorizationColor: <color> }`. Qt6's `MultiEffect.colorization` blends toward `colorizationColor` weighted by the source pixel's own luminance rather than fully overwriting every opaque pixel to a flat color — it behaves like a duotone/tint effect, not a flat recolor. Since Adwaita's `network-wireless-symbolic.svg` fills with a fairly dark grey (`#2e3436`, confirmed in the investigation above), colorizing it "to white" at `colorization: 1.0` never actually reached pure `#ffffff` — it landed on a dimmer, greyish tone, which is exactly what the user was seeing and (correctly) not accepting as a hardware limitation.

**Fix**: replaced the colorization approach with a flat-fill-via-alpha-mask technique (the same `MultiEffect { maskEnabled: true; maskSource: ... }` mechanism just established elsewhere this session for rounding the idle pill's album-art thumbnail) — a solid `Rectangle` colored `rowIcon.iconColor` is drawn as the effect's `source`, masked by the icon's own alpha shape (`maskSource: iconImg`) instead of colorizing the icon directly. This guarantees every visible pixel is the *exact* flat target color, completely independent of the source glyph's internal shading — a `colorizationColor: "#ffffff"` icon now renders genuinely, provably white. Scope: only `IslandHeaderRow.qml`'s `RowIcon` (battery/wifi/bluetooth/gear icons in the media card header) was changed in this pass. `MediaControls.qml`'s `MediaButton` and `DynamicIsland.qml`'s OSD icons use the identical colorization pattern and likely have the same dimming issue, but weren't touched here — worth applying the same fix there if the user notices the same problem on those.

`qs` log clean (headless + live-restarted real instance), no errors.

## Extension 6, Round 1 — debug pass fixes (2026-09-13, later same day)

Independent verification found and fixed two real bugs before live-testing:

1. **Anti-corner ears were inverted.** Traced the `destination-out` arc geometry by hand: the original code centered the erasing quarter-circle on the corner that TOUCHES notch (the near corner), which erases exactly the material that should stay and flare into notch, leaving the *far* corner's material intact instead — the opposite of a flare. ## Mic false-positive, part 2 — the PipeWire check itself was also affected (2026-09-13, later same day)

## Extension 16 debug pass — real orphaned-process leak found and fixed (2026-09-16)

Independent verification found a genuine bug the build agents' own testing didn't catch (it wasn't a code-correctness issue, an operational one): `ps aux` showed **four** `localsend_discover.py` processes running simultaneously, all but one reparented to PID 1 (orphaned). Root cause: this script is a deliberately long-running `while True: recvfrom()` loop, and this project's established restart procedure (`qs list` → `kill <pid>` → relaunch, used dozens of times across today's session) sends `SIGTERM` only to the `qs` process itself — POSIX does not propagate that to child processes, so every single restart left the previous `discover.py` running forever as an orphan. `SO_REUSEADDR` let each new copy bind the same multicast port without ever erroring, so nothing surfaced the accumulation on its own.

**Fixed**: `localsend_discover.py` now writes its own PID to `/tmp/localsend_discover.lock` on startup, and — before doing so — reads any PID already there and sends it `SIGTERM` (swallowing `ProcessLookupError`/`FileNotFoundError` cleanly for the normal "no previous instance" case). A fresh launch now self-cleans its predecessor regardless of how the parent `qs` was restarted, instead of relying on the parent to clean up after itself. Killed the three pre-existing orphans by hand, correctted the lock file to point at the (at-the-time) genuine live instance's PID so the fix would correctly take over on the very next restart, then did a real restart to confirm: exactly one `localsend_discover.py` survived afterward, the stale one was actually terminated by the new one, `qs` loaded clean (PID 105488, then its own discoverer 105510).

Also confirmed clean by direct inspection (no fix needed): `LocalSendMonitor.qml`'s `Process`/`Timer` wiring (single reused `sendProc`, correct JSON-parse try/catch, correct 30s stale-device pruning); both Python scripts' argv-list invocation (no shell interpolation of file paths/device data anywhere); `localsend_send.py`'s sha256 is computed before any network call; `DropArea` doesn't conflict with the pill's existing `MouseArea`s (different Qt event types — `DropArea` only reacts to drag/drop, never intercepts clicks); `closeAllPanels()` correctly includes `localSendActive = false`, so this isn't a new instance of the earlier panel-mutual-exclusion bug class; `displayState` priority (`localsend` sits below the transient OSDs, above `overview`/`mediaExpanded`) is coherent.

## LocalSend real two-way transfer — three real bugs found and fixed via live phone testing (2026-09-17)

The user did a genuine live test (real phone, real files) that this project's prior LocalSend rounds (Extensions 16/24/35) had never actually completed end-to-end. Three separate, real, independently-confirmed bugs surfaced in sequence — each found by adding a temporary diagnostic (a `/tmp/*.log` write, removed again once confirmed) and re-testing live with the phone, not guessed from reading the code:

1. **Receiving from the phone always failed with HTTP 422** (`localsend_server.py`'s `_handle_upload`). Root cause: `_read_body()` only ever read `Content-Length` bytes, defaulting to reading **zero bytes** when absent — and the real Android LocalSend client uploads the file body with `Transfer-Encoding: chunked` and no `Content-Length` at all (confirmed via a temporary diagnostic: `bytesRead: 0`, `actualSha256` was the well-known empty-string hash). `http.server.BaseHTTPRequestHandler` doesn't decode chunked *request* bodies on its own. Fixed by manually parsing chunked encoding in `_read_body()` (hex size line → that many bytes → trailing CRLF, repeated to a 0-size terminator chunk).
2. **The island never showed the phone as a device to send TO**, even though the phone could already see and send to the island. Root cause: a real Android LocalSend client apparently never multicasts its own presence — it only ever *replies* to OUR multicast announce with a direct unicast HTTP POST to `/api/localsend/v2/register`, confirmed via a live capture of that exact POST body (`alias: Aaronfox, deviceModel: Xiaomi, fingerprint: AF4EB9...`). `localsend_server.py`'s `/register` handler read that body and just discarded it — `LocalSendMonitor.qml`'s `devices` list was only ever fed by `localsend_discover.py`'s multicast listener, which this kind of peer never actually reaches. Fixed by having the `/register` handler forward the peer's info as a stdout event (reusing the existing `log()` JSON-line convention) and having `LocalSendMonitor.qml` merge it into the same `devices` list via a new shared `mergeDevice()` function (factored out of `listenerProc`'s handler, now called from both `listenerProc` and `serverProc`'s stdout parsers).
3. **Sending from the island to the phone failed with `SSL: TLSV13_ALERT_CERTIFICATE_REQUIRED`.** Root cause: the real LocalSend HTTPS model is mutual TLS — the receiving phone's server sends a `CertificateRequest` during the handshake and fatally aborts if the connecting client doesn't present one, independent of whether the client verifies the server's own cert. `localsend_send.py`'s SSL context only ever set `verify_mode = CERT_NONE` (not verifying the *server*) but never loaded a client certificate of its own. Fixed by loading the same persisted `localsend_cert.pem`/`localsend_key.pem` pair the receiver side (`localsend_server.py`) already uses as this device's fixed identity, via `ctx.load_cert_chain(...)`, with the same `ensure_cert()` generate-once-if-missing pattern duplicated locally (matching this project's small-single-purpose-script convention rather than a shared import).

All three confirmed via the user's own real phone — not just headless/log-clean checks, which none of these three bugs would have surfaced in (no QML error, no crash, just wrong protocol behavior). **Real two-way file transfer between this laptop and the phone is now confirmed working in both directions.**

## Weather — Wi-Fi positioning (2026-10-03)

IP geolocation was ISP-level: every provider tested (ip-api, ipinfo, ipwho, ipapi.co, geojs) placed the DIGI IP at Kecskemét's centroid, so a better IP database can't fix it, and the T480 has no GPS/WWAN. New `wifi_locate.py` (stdlib only) reads the cached NetworkManager scan (`nmcli -t -f BSSID,SIGNAL dev wifi list --rescan no`, strongest 12 APs). It asks Apple's Wi-Fi positioning service (unofficial `gs-loc.apple.com/clls/wloc`, hand-encoded protobuf; unknown BSSIDs come back at latitude -180°, and Apple strips leading zeros per octet) and takes a signal-weighted centroid. If Apple knows none of the APs it falls back to BeaconDB (open, but it knew none of the APs here), then reverse-geocodes through Nominatim (zoom 10, city/town/village). It prints one JSON line on success, or exits 1. `WeatherMonitor.refreshLocation()` runs it first and falls back to ip-api.com on a nonzero exit code (decided in `onExited`, not in the stdout handler, since the collector's text can arrive after `exited`). `locationSource` gained `"wifi"` ("Wi-Fi location" in the panel subtitle). The location re-resolve timer went from 3 h to 30 min so a moving laptop follows along. Verified live: Kecskemét 46.91816, 19.66841 (Apple, ±20 m) through the running `qs` instance, with a temporary probe that was removed afterwards. An Időkép scrape for Hungary was tried and reverted at the user's request: the project is meant to be global.
